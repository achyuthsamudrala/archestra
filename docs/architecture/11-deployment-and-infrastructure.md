# Deployment & Infrastructure

Archestra ships as one Docker image (`platform/Dockerfile`) that can be run three different ways depending on how much production infrastructure the deployer wants to own: a single `docker run` for evaluation, a Helm chart onto an existing Kubernetes cluster for production, or (during local development) a Tilt-orchestrated mix of Kubernetes and host processes. The throughline across all three is that **Kubernetes is not optional infrastructure bolted on for scale — it's part of the product**: the MCP orchestrator described in the README ("MCP orchestrator with a Kubernetes operator") *is* a Kubernetes controller that creates one pod per MCP server, and the skill-execution sandbox needs a container runtime (Dagger) that itself needs a place to run. Every deployment topology below exists to answer "where does that Kubernetes cluster come from."

See also [Backend Architecture](./02-backend.md) and [MCP Gateway & Orchestrator](./05-mcp-gateway-and-orchestrator.md) for what actually runs inside the pods this document describes provisioning, and [Observability](./10-observability.md) for the metrics/tracing endpoints these deployments expose.

## Deployment topologies

### 1. Quickstart: single container, embedded Kubernetes

```bash
docker pull archestra/platform:latest
docker run -p 127.0.0.1:9000:9000 -p 127.0.0.1:3000:3000 \
   -e ARCHESTRA_QUICKSTART=true \
   -v /var/run/docker.sock:/var/run/docker.sock \
   -v archestra-postgres-data:/var/lib/postgresql/data \
   -v archestra-app-data:/app/data \
   archestra/platform
```

This is documented in `docs/pages/platform-deployment.md`. `ARCHESTRA_QUICKSTART=true` plus a mounted Docker socket makes the container's entrypoint (`platform/docker/scripts/docker-entrypoint.sh`) create a **KinD (Kubernetes-in-Docker) cluster inside the container's own Docker daemon access**, name it `archestra-mcp`, and use it as the backing cluster for the MCP orchestrator — so `docker run` alone gets a working, pod-per-MCP-server runtime without the user ever installing `kubectl` or standing up a cluster. The entrypoint also generates and persists an `ARCHESTRA_AUTH_SECRET` to `/app/data/.auth_secret` if one isn't supplied, and tears the KinD cluster down on container shutdown if it created it. PostgreSQL runs *inside the same container* (bundled via `apk add postgresql17 postgresql17-contrib postgresql-pgvector`, managed by `supervisord`) unless `ARCHESTRA_DATABASE_URL` points elsewhere — named volumes (`archestra-postgres-data`, `archestra-app-data`) are what make Postgres data and the auth secret survive a container restart.

The tradeoff is explicit in the CLI warning text baked into the entrypoint: mounting `/var/run/docker.sock` gives the container root-equivalent access to the host's Docker daemon. This is acceptable for a local evaluation instance, never for a production deployment — the docs explicitly say so.

### 2. Helm on an external Kubernetes cluster (production)

`platform/helm/archestra/` is the production path. It deploys the same `archestra/platform` image (no embedded KinD; `ARCHESTRA_QUICKSTART` is not part of this path) against a real cluster, with:

- `archestra-platform.yaml` — the main web Deployment (backend API on 9000, metrics on 9050, frontend on 3000, all in one pod/container — this is the same unified image, just without the quickstart KinD path).
- `archestra-worker.yaml` — an optional, separately-scaled Deployment for background job processing (knowledge-base connector syncs, batch embeddings) when `archestra.worker.enabled` is true; the web pods then run `ARCHESTRA_PROCESS_TYPE=web` only instead of running the worker in-process.
- `migration-job.yaml` — a Helm pre-upgrade hook Job that runs `pnpm db:migrate` before new pods roll out, with a `PGOPTIONS` `lock_timeout` (default `5s`) so a migration that would block on an `ACCESS EXCLUSIVE` lock against live traffic fails fast and aborts the upgrade instead of stalling every query on that table.
- `mcp-serviceaccount.yaml` / `code-runtime-rbac.yaml` / `code-runtime-dagger-serviceaccount.yaml` — RBAC wiring for two different privileged operations: the platform's own ServiceAccount managing MCP server pods (create/delete pods, services, deployments, jobs in the target namespace), and a separate, narrowly-scoped Role letting the platform `kubectl exec` into the Dagger Engine pod for skill sandboxing.
- `dagger-network-policy.yaml` — an egress NetworkPolicy for the managed Dagger Engine pod, on by default (enforcement depends on the cluster's CNI supporting NetworkPolicy).
- `horizontal-pod-autoscaler.yaml`, `pod-disruption-budget.yaml`, `gke-backend-config.yaml` — standard production scaling/availability primitives, all opt-in (`enabled: false` by default) except the sizing already reflects real operational lessons: the default Postgres memory limit (2Gi, above the 1Gi request) exists because "a hard 1Gi ceiling has OOM-killed the bundled instance under load" (`values.yaml` comment), and `max_connections = 250` is sized explicitly against worst-case pod count (web + worker + rollout surge + migration job + metrics exporter).
- A vendored `dagger-helm` subchart (`charts/dagger-helm-0.21.5.tgz`, aliased `dagger`) and `postgresql` subchart (Bitnami, `charts/postgresql-18.0.8.tgz`) — Postgres is optional (`postgresql.enabled: false` plus `external_database_url` to point at RDS/Cloud SQL instead; the image already vendors both providers' CA bundles into `NODE_EXTRA_CA_CERTS` for `sslmode=require`).

The chart's `orchestrator.kubernetes` values section (`values.yaml`) controls how the platform *itself* talks to the cluster it's deployed on to manage MCP server pods: in-cluster config via its own ServiceAccount (`loadKubeconfigFromCurrentCluster: true`, the default and typical production setting) or a mounted kubeconfig Secret for out-of-cluster orchestration. This maps directly to the backend env vars `ARCHESTRA_ORCHESTRATOR_KUBECONFIG` / `ARCHESTRA_ORCHESTRATOR_LOAD_KUBECONFIG_FROM_CURRENT_CLUSTER` / `ARCHESTRA_ORCHESTRATOR_K8S_NAMESPACE` (`platform/backend/src/config.ts`), which together gate the `orchestratorK8sRuntime` feature flag returned by `/api/features` — the frontend disables local-MCP-server functionality entirely when neither is configured.

### 3. Local development: Tilt + K8s + host processes (hybrid)

Local dev doesn't run the production Docker image at all — `tilt up` orchestrates a mix: PostgreSQL runs in Kubernetes (`platform/dev/Tiltfile.database`, namespace `archestra-dev` by default via `ARCHESTRA_K8S_NAMESPACE`), while the backend and frontend run as plain host processes (`pnpm dev --filter @backend` / `@frontend`) for fast reload. `platform/Tiltfile` loads sub-Tiltfiles by concern (`Tiltfile.database`, optionally `Tiltfile.coderuntime` when `ARCHESTRA_CODE_RUNTIME_ENABLED=true`, optionally `Tiltfile.minio` for S3-mode file storage, `Tiltfile.dev`, `Tiltfile.test`, `Tiltfile.integrations`). The MCP orchestrator's RBAC template is rendered from the *same* Helm chart used in production (`helm template archestra-platform ../helm/archestra ... --show-only templates/mcp-serviceaccount.yaml`, in `Tiltfile.database`) — so local dev exercises the identical RBAC shape production gets, rather than a hand-maintained dev-only YAML that could drift. The `observability` stack (Tempo/Loki/OTel Collector/Prometheus/Grafana) is a separate, manually-started Tilt resource wrapping `docker-compose.observability.yml` — see [Observability](./10-observability.md).

## The Dockerfile: what one image contains

`platform/Dockerfile` is a multi-stage build that produces a single image serving backend, frontend, and (for quickstart) an embedded Kubernetes control plane:

1. **`go-builder`** — compiles KinD, the Docker CLI, the Dagger CLI, and `kubectl` **from source**, pinned to specific commits, rather than downloading prebuilt binaries. The comments in the Dockerfile explain why: Alpine's packaged Go toolchain lags upstream patch releases, and building from source lets the team apply targeted `go get` CVE bumps (there are a dozen explicit CVE-driven dependency pins in this stage alone, e.g. `golang.org/x/net@v0.55.0` for CVE-2026-39821) without waiting on upstream projects to cut new releases.
2. **`dagger-manifest`** / **`dagger-engine-image`** — renders the `helm/dagger-runtime` chart into a static manifest and pre-pulls the Dagger Engine image as a `docker-archive` tarball at *build* time, so the quickstart path can `kind load` it into the embedded cluster offline instead of pulling ~352MB from a registry on every container boot (KinD recreates its node on every run, and that node's containerd can't see the host's Docker image cache).
3. **`deps` / `builder-base` / `builder`** — standard pnpm monorepo build: install with `--frozen-lockfile`, compile the Rust NAPI addons (`archestra-rs/*`), run `pnpm build` (frontend + backend), then `pnpm deploy --filter=@backend --prod --legacy` to assemble a self-contained backend tree (this replaced an earlier hand-rolled copy of each NAPI crate's `.node`/`index.cjs`, which had dropped a dependency and crashed the image with `MODULE_NOT_FOUND`).
4. **`unified-slim`** — the runtime image: Node 24 Alpine base, PostgreSQL 17 + pgvector installed via `apk`, `supervisord` for process management, the from-source KinD/Docker-CLI/`kubectl`/Dagger CLI binaries copied in, the built backend (`pnpm deploy` output) and frontend (`next build`'s standalone server) copied in. `unified-slim` deliberately excludes the ~352MB Dagger Engine tarball so CI's e2e shards (which build `--target unified-slim`) never pay that cost.
5. **`unified`** — `unified-slim` plus the pre-baked Dagger Engine tarball layered on top. This is the default build target (no `--target` flag) and what `docker pull archestra/platform:latest` resolves to — it must remain the last stage in the file so ordinary builds (releases, quickstart CI, fork PRs, local `docker build`) get the full, offline-capable image.

Frontend static assets get special handling: `COPY prev-static-assets/ ./frontend/.next/static/` copies in the *previous* release's Next.js static assets (content-hashed filenames avoid collisions) before overlaying the current build's assets on top, and a clean copy of only the current build's assets is written to `/static-assets-source/` for CI to extract as input to the *next* release's `prev-static-assets/`. This exists so that clients with an old build cached in the browser (e.g. a long-lived tab open across a deploy) can still fetch their old chunk after the server rolls to a new version, instead of hitting a 404 on a static asset that no longer exists in the new image.

The image also carries a running list of manually-applied CVE patches for things `pnpm overrides` can't reach — e.g. a vendored `picomatch` copy inside Next.js's compiled output (`frontend/node_modules/next/dist/compiled/picomatch`), patched by downloading and extracting the fixed version directly over the vendored copy, verified by SHA-256, because Next.js hadn't re-vendored yet upstream.

## MCP server & sandbox base images

Two other Dockerfiles under `platform/` back the workloads the orchestrator schedules, both minimal by design since they run untrusted-ish, third-party code:

- **`platform/mcp_server_docker_image/`** — the base image (`gcr.io/archestra-ai/mcp-server-base`) for K8s-run MCP servers: Python 3.12 + Node 20, MCP SDKs for both, a non-root user (uid/gid 1000), multi-stage build for a minimal final image. MCP servers run with dynamic command/args (`docker run mcp-server-base <command> <args>`) rather than baking a specific server into the image, so one base image serves every stdio/streamable-http MCP server the orchestrator launches. Python deps are pinned via `requirements.lock` compiled from `pyproject.toml` with `uv`.
- **`platform/sandbox_base/`** — the pre-built execution base for the Dagger skill sandbox. It exists purely as a performance/isolation optimization: it pre-bakes exactly what `build_warm_base()` (`archestra-rs/sandbox-core/src/backends/dagger.rs`) would otherwise construct at *run* time (apt packages, a `pip`→`uv` shim, a uv project, a venv with default deps). Pointing `ARCHESTRA_DAGGER_RUNTIME_IMAGE` at a published build of this image with `ARCHESTRA_CODE_RUNTIME_BASE_PREBUILT=true` lets the sandbox skip that build step entirely, so a network-restricted Dagger engine needs no egress to `ghcr.io`/Debian mirrors/PyPI at run time — only to the registry hosting this one image. Its README requires it stay in lockstep with the `DEFAULT_*` constants in `dagger.rs`, enforced by a `check:sandbox-base` CI job.

## Licensing enforcement: AGPL default, Enterprise by marker

The repo is dual-licensed (`LICENSE.md` at the repo root is the router): AGPL-3.0-only by default (`LICENSE_AGPL`), or `LicenseRef-Archestra-Enterprise` (`LICENSE_ENTERPRISE`) for code explicitly marked as such. Resolution is first-match-wins across three mechanisms, all machine-checkable rather than relying on a human remembering which directory is which:

1. **SPDX file header** — a file-level `// SPDX-License-Identifier: LicenseRef-Archestra-Enterprise` header is authoritative for that whole file. Example in the codebase: `platform/backend/src/enterprise-tier.ts` opens with exactly this header.
2. **In-file REUSE snippet regions** — `// SPDX-SnippetBegin` / `// SPDX-SnippetEnd` wrapping a region marks *just that region* Enterprise, leaving the rest of the file AGPL, using each language's native comment syntax.
3. **Path convention** — any `*.ee.{ts,tsx,js,jsx,py,rs,sql,json,yaml,yml,md}` file, or anything under an `ee/` directory, is Enterprise by naming convention alone.

Pricing/feature scope is documented separately in `docs/pages/platform-pricing-model.md`; `LICENSE.md` only governs which license text applies to which code.

Runtime gating layers on top of the license tagging via `EnterpriseTierService` (`platform/backend/src/enterprise-tier.ts` — itself Enterprise-licensed code, tagged with the SPDX header above). It resolves feature activation from two independent signals: an explicit `ARCHESTRA_ENTERPRISE_*` env flag (`config.enterpriseFeatures.core`), **or** a "small team" carve-out — Enterprise-tier features (`core`, `knowledgeBase`) are active for any organization under 30 users (`SMALL_TEAM_THRESHOLD`) regardless of license flag, refreshed every 60 seconds from a live `UserModel.countAll()` query. On the very first refresh (before the DB is reachable), the service defaults to small-team-active rather than inactive, so a fresh deployment doesn't lose Enterprise features before Postgres is up. This means Enterprise code paths are not simply "off unless licensed" — they're on by default for small deployments and gated by user count for larger ones, which is a product decision (free trial-by-scale) implemented as an observability-adjacent service rather than a licensing check per se.

## Supply-chain security posture

Two settings in `platform/pnpm-workspace.yaml` are the project's primary defense against npm supply-chain attacks (malicious postinstall scripts, typosquats, compromised maintainer accounts publishing a bad patch release):

- **`ignoreScripts: true`** — disables automatic execution of `preinstall`/`postinstall`/`install` scripts for every package in the workspace. These scripts run arbitrary code with the installing user's privileges and are a common attack vector (exfiltrate env vars/secrets, install a backdoor) precisely because they execute silently during a routine `pnpm install`. Packages that legitimately need a build step are rebuilt explicitly and individually: `pnpm rebuild <package-name>`.
- **`minimumReleaseAge: 10080`** (minutes = 7 days) — a package version cannot be installed until 7 days after it was published to the registry. Malicious releases are typically caught and pulled within hours of publication once the community notices; a 7-day floor means the workspace never installs a version during that high-risk window. `minimumReleaseAgeExclude` carves out narrow, deliberate exceptions (e.g. `next`/`@next/*` while validating a canary fix for a known memory leak) — each exclusion in the file is commented with the reason and is expected to be temporary, swept later by the `archestra-dev-override-sweep` skill once the real fix has cleared the window on its own.

Both settings trade a small amount of developer friction (an occasional manual `pnpm rebuild`, or a short wait before a brand-new dependency version is installable) for meaningfully reduced blast radius from a compromised package. `overrides` in the same file additionally pin specific transitive dependencies past known-CVE floors (e.g. `'@fastify/reply-from': '>=12.6.2'`) where waiting on an upstream package to bump its own dependency isn't practical.

## Environments: egress policy as a first-class deployment concept

Beyond the cluster/image level, `docs/pages/platform-environments.md` describes an organization-level deployment-target concept (`sandbox`, `staging`, `production`, …) that scopes *what a running agent or MCP gateway can reach*, independent of the Kubernetes/Helm topology it happens to run on. Each environment carries an optional Kubernetes namespace and an optional network egress policy, applied to both MCP server pods and agent code sandboxes. Every organization has an implicit **Default** environment; resources with no environment set belong to it, and Default is a strict peer of named environments (not a wildcard) — a Production-scoped agent cannot see Default's tools any more than it can see Staging's. Restricted environments require the `environment:deploy-to-restricted` permission to assign resources into, letting an org lock down who can point an agent at production credentials/tools without restricting who can merely view the environment list. This is enforced at the same layer that decides which MCP servers, knowledge connectors, and skills an agent/gateway is allowed to see — see [MCP Gateway & Orchestrator](./05-mcp-gateway-and-orchestrator.md) — and is paired with per-environment cost limits (`docs/pages/platform-pricing-model.md`) so a runaway agent in a sandbox environment can't burn a production budget.

## Design Decisions & Tradeoffs

- **Kubernetes is required for the MCP orchestrator, rather than running MCP servers as plain Docker containers.** MCP servers need per-server lifecycle management (start/restart/stop), two transport modes (stdio via `kubectl attach`-style proxying, streamable-http via a K8s Service), log streaming, and namespace-scoped isolation between environments. Docker alone has no equivalent of a Service/DNS abstraction, no declarative desired-state reconciliation, and no per-namespace RBAC boundary — all of which the orchestrator needs to safely run a customer's arbitrary third-party MCP servers. The cost is that *every* deployment path, including the single-container quickstart, must produce a Kubernetes cluster from somewhere — hence KinD-in-Docker for quickstart rather than a lighter-weight non-K8s fallback.
- **Quickstart embeds a whole KinD cluster inside one container rather than requiring the user to run `docker compose` with a separate K8s dependency.** This keeps the "try it" experience to one `docker run` command, at the cost of requiring the Docker socket to be mounted (root-equivalent host access) and pre-baking a ~352MB Dagger Engine image into the release artifact so quickstart works offline. The docs are explicit that this mode is development-only.
- **Dual licensing (AGPL default + Enterprise marker) in one repository, rather than splitting Enterprise code into a private/separate repo.** Keeping everything in one tree means Enterprise code is reviewed, tested, and released alongside the AGPL core with the same CI, and contributors don't need access to a second repo to understand a feature end-to-end. The cost is that license boundaries must be enforced by convention + tooling (SPDX headers, `*.ee.*` naming, REUSE snippet regions) rather than by repository ACLs — a missing or wrong header is a possible (if checkable) mistake in a way that "wrong repo" cannot be.
- **`EnterpriseTierService` gates features by live user count, not solely by license flag.** A pure license-flag gate would mean every small/free deployment loses Enterprise features outright. Auto-activating for teams under 30 users turns Enterprise gating into "free at small scale, licensed at large scale" without a separate free tier's worth of product/billing logic — but it means the same code path behaves differently depending on organization size, which is a subtlety anyone reading `enterprise-tier.ts` for the first time needs to understand before assuming "Enterprise" means "requires a license."
- **`minimumReleaseAge: 7 days` (not, say, 24 hours or 30 days).** This mirrors community guidance (cited directly in the file: daniakash.com's "simplest supply chain defense") that most malicious npm releases are caught and yanked within hours to a couple of days of publication. Seven days is long enough to clear that detection window with margin, short enough that legitimate dependency updates (including CVE fixes contributors want to pull in quickly) aren't stuck waiting a month — hence the narrow, commented `minimumReleaseAgeExclude` escape hatch for cases where waiting the full week would leave a known vulnerability unpatched longer than accepting the small supply-chain risk.
- **Single-container quickstart vs. full Helm chart is a deliberate two-tier complexity split, not a spectrum.** There's no "medium" deployment option (e.g. `docker compose` with an external K8s dependency) offered as a first-class documented path — a user either takes the zero-infrastructure quickstart (embedded KinD, single-node, not for production) or the full Helm chart (external cluster, HPA, PDB, migration Job, worker Deployment, GKE BackendConfig, managed Dagger Engine). This keeps the number of supported topologies small (two, not three or four), at the cost of a possibly steep jump in operational surface area between "trying it out" and "running it for real."
- **The migration Job runs as a Helm pre-upgrade hook with a hard `lock_timeout`, rather than letting migrations run inline in the web Deployment's startup.** Running as a separate hook Job means the previous release's web pods keep serving traffic while the schema migrates, and the `lock_timeout` (default `5s`) makes a migration that would otherwise queue behind live `ACCESS EXCLUSIVE`-locked queries fail fast and abort the upgrade cleanly rather than silently stalling every query against that table for the duration of a blocked DDL statement.
