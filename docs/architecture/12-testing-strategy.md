# Testing Strategy

Archestra's `platform/` monorepo runs four largely independent test layers — backend unit/integration tests (Vitest + PGlite), frontend integration tests (Playwright + MSW), end-to-end tests (Playwright against a real deployed stack), and Rust checks (cargo) — plus two purpose-built linters (`drizzle-migration-linter`, the license/supply-chain scripts) and a separate performance-benchmark harness. This document covers how each layer is built, why it's built that way, and how Turborepo and GitHub Actions stitch them into the PR pipeline. For the agentic-eval harness (a different kind of "benchmark" entirely), see [AI Labs Benchmark](./13-ai-labs-benchmark.md).

## Backend unit/integration tests: Vitest + PGlite

Backend tests never mock the database. Every test file gets a real Postgres-compatible database — [`@electric-sql/pglite`](https://github.com/electric-sql/pglite), an in-memory WASM build of Postgres — migrated with the project's actual Drizzle migrations, and test code goes through real model methods (`platform/CLAUDE.md`, `.claude/skills/archestra-dev-backend-tests/SKILL.md`). This is a deliberate rejection of mocking the ORM/DB layer: a mocked query builder can't catch a bad `JOIN`, a missing index-backed constraint, or a Drizzle/Postgres type mismatch, and Archestra's model layer (`backend/src/models/`) is where most business-logic bugs actually live.

**Two-tier setup for migration cost.** Replaying ~270 migration files (`backend/src/database/migrations/`, ~41 MB of SQL) inside every one of 400+ test files' `beforeAll` was, per the code comments in `platform/backend/src/test/global-setup.ts`, "the dominant cost of a run" (~100k migration executions per suite). The fix is a two-stage build:

1. **`global-setup.ts`** (Vitest `globalSetup`, runs once for the whole process, before any worker starts) replays every migration into a scratch PGlite instance, then `dumpDataDir("gzip")`s the fully-migrated database to a temp file and hands the path to workers via `ARCHESTRA_TEST_PGLITE_SNAPSHOT_PATH`.
2. **`setup.ts`** (Vitest `setupFiles`, runs per file) loads that snapshot with `new PGlite({ loadDataDir: snapshot })` in `beforeAll` — a flat cost regardless of migration count — and falls back to replaying migrations directly only if no snapshot env var is present (e.g. a tooling path that skips `globalSetup`).

Per-test isolation then comes from `TRUNCATE ... RESTART IDENTITY CASCADE` across every non-`drizzle_%` table in `beforeEach` (`platform/backend/src/test/setup.ts`), not from tearing down and rebuilding the database — truncation is orders of magnitude cheaper than a fresh migration replay. `setup.ts` deliberately does **not** seed an organization or default agent; tests opt into that state via fixtures (`makeOrganization`, `makeAgent`, ...) so a test can also exercise the "no organization yet" path.

The migration SQL itself is read once and cached (`platform/backend/src/test/migrations-helper.ts`), shared between the `globalSetup` builder and `setup.ts`'s fallback path so the two call sites can't drift.

**Forks, not threads.** `platform/backend/vitest.config.ts` pins `pool: "forks"` explicitly, with a comment noting that PGlite (a WASM module) sharing one process-global V8 JIT-page registry across worker *threads* intermittently aborts the whole process with a fatal `Check failed: jit_page.has_value()`. Forks give each worker its own V8 process, so the registry can't race. Worker count is bounded by **both** CPU and memory: locally, half the available cores (leaving the machine usable); on CI, all cores, but capped at `os.totalmem() / 5 GB` per fork, because each fork independently loads the full module graph plus its own PGlite WASM instance (up to ~3 GB RSS per fork) rather than sharing one address space the way the threads pool would.

### The `clean` / `mocked` project split (the "shared-worker fast path")

`vitest.config.ts` partitions every `*.test.ts` file at config-load time by grepping its source for `\bvi\.(mock|doMock|unmock|doUnmock|hoisted)\(` (`partitionTestFiles()` in `platform/backend/vitest.config.ts`):

- **`clean` project** — files with no module-mock calls run with `isolate: false`. Vitest workers share their module cache across files in this project, so the backend's full module graph (auth, config, database, every model) is imported once per *worker*, not once per *file* — the CLAUDE.md skill cites this as saving roughly 6 seconds per file.
- **`mocked` project** — any file using `vi.mock`/`vi.doMock`/`vi.hoisted` keeps full isolation (`isolate: true`), because Vitest does not reset its module-mock registry between files sharing a worker ([vitest-dev/vitest#4894](https://github.com/vitest-dev/vitest/issues/4894)) — an unmocked file could silently inherit another file's mock.

Routing is automatic and content-derived: a new test that adds `vi.mock` moves itself into the isolated project on the next run, with no list to maintain. The practical consequence documented in `.claude/skills/archestra-dev-backend-tests/SKILL.md` is a house style: prefer **not** mocking modules at all, and when an HTTP client needs faking, mock at the network boundary with MSW (`platform/backend/src/test/msw.ts`, `useMswServer()`) instead of `vi.mock`-ing the client library — this keeps the file in the fast `clean` project and exercises the real client's request-building/retry logic against a faked wire.

Because the `clean` project shares module state across a worker's files, `setup.ts` restores a pristine deep-clone of the `config` singleton before **and** after every test (`restoreConfig()`), so a test-local `config.foo = true` mutation can't leak into the next test or, in shared workers, the next *file*. The `mocked` project skips this because each file already gets a clean module registry.

### Fixtures (`@/test`)

`platform/backend/src/test/fixtures.ts` extends Vitest's `test`/`beforeEach` context (via `test.extend`, per [Vitest's test-context fixture pattern](https://vitest.dev/guide/test-context.html#extend-test-context)) with factory functions for every core entity: `makeUser`, `makeAdmin`, `makeOrganization`, `makeTeam`, `makeTeamMember`, `makeAgent`, `makeInternalAgent`, `makeTool`, `makeAgentTool`, `makeApp`, `makeAppVersion`, `makeToolPolicy`, `makeTrustedDataPolicy`, `makeCustomRole`, `makeMember`, `makeMcpServer`, `makeInternalMcpCatalog`, `makeInvitation`, `makeAccount`, `makeSession`, `makeKnowledgeBase`, `makeConnectorRun`, `makeConversation`, `makeInteraction`, `makeSecret`, `makeLlmProviderApiKey`, `makeIdentityProvider`, `makeOAuthClient`, and `seedAndAssignArchestraTools`, among others. Each factory writes through the real model layer where one exists (e.g. `makeAgent` calls `AgentModel.create`) rather than raw `db.insert`, and auto-creates dependent entities when omitted (e.g. `makeAgent()` with no `organizationId` calls `makeOrganization()` first). `platform/backend/src/test/route-test-app.ts` layers a `useRouteTestApp(routes)` helper on top that boots a real Fastify instance around a route plugin with a stubbed authenticated request context, for route-level tests that exercise HTTP handling without a full server.

### Module mocking rules (when mocking is unavoidable)

`@/auth`, `@/auth/utils`, `@/observability`, `@/cache-manager`, and `@/logging` each have a canonical mock resolved via Jest-style `__mocks__` directories, activated with a bare `vi.mock("@/auth")` (no factory) — `.claude/skills/archestra-dev-backend-tests/SKILL.md` warns against ever hand-rolling a partial factory for these, and against mixing a bare `vi.mock(x)` with a factory `vi.mock(x, ...)` for the same specifier across different files, since Vitest can silently pick one depending on file execution order ([vitest-dev/vitest#10145](https://github.com/vitest-dev/vitest/issues/10145)). `@/config` uses a deep-merge factory (`configModuleMock(overrides)` from `platform/backend/src/test/mocks/config.ts`) so unspecified keys keep their real values — a hand-rolled `{ default: { kb: {...} } }` would silently drop the rest of the config object. Global stubs (`vi.stubGlobal`, `vi.stubEnv`) must be (re-)applied inside `beforeEach`, not only at module scope, because `unstubGlobals: true` / `unstubEnvs: true` in `vitest.config.ts` auto-reverts every stub after each test — a module-scope-only stub silently vanishes after the first test in the file.

### Performance discipline

CI shards the backend suite across 4 parallel jobs (`vitest run --shard=k/4`, `.github/workflows/on-pull-requests.yml` → `backend-unit-tests`), gated behind a stable-named `backend-unit-tests-gate` job so branch protection has one required check regardless of shard count. `maxConcurrency` is raised to 12 on CI vs. 6 locally, and `sequence.shuffle: true` shuffles test file order to balance load. Because the `clean` project's dominant cost is module-import time, `.claude/skills/archestra-dev-backend-tests/SKILL.md` calls out that heavy new top-level imports in widely-imported modules cost every worker — test-only helpers belong under `src/test/`, not inline in product modules.

## Frontend integration tests: Playwright + MSW

A separate suite from both backend Vitest and the full e2e suite, run via `pnpm test:integration` and gated as `frontend-integration-tests` in `.github/workflows/on-pull-requests.yml`. It runs Playwright against the Next.js frontend with network calls intercepted by MSW rather than a real backend — fast, browser-real DOM/React behavior without booting Postgres, Fastify, or Kubernetes. The workflow only installs the Chromium browser (cached by Playwright version) since these tests don't need cross-browser coverage — that's the e2e suite's job.

## End-to-end tests: Playwright against a real stack

`platform/e2e-tests/` (`.claude/skills/archestra-dev-e2e/SKILL.md`, `platform/e2e-tests/playwright.config.ts`) runs Playwright against a fully deployed Archestra stack — real Fastify backend, real Postgres, real Kubernetes-backed MCP server runtime — across chromium, webkit, and firefox (`pnpm test:e2e`).

**Project topology, not just browsers.** `playwright.config.ts` defines Playwright *projects* along two axes: setup ordering (`setup-admin` → `setup-users` → `setup-teams`, each depending only on the prior setup project, never on other test projects — a comment explains this is deliberate so sharding can distribute test files without pulling in whole dependency chains) and environment shape:
- `chromium`/`firefox`/`webkit` — the main UI suite (`uiTestMatch`), tagged `@firefox`/`@webkit` tests only run under those browsers via `grep`.
- `api` — pure API integration specs that don't need a browser, running in the "lite" environment (platform as a single quickstart-mode container plus WireMock/Keycloak sidecars — MCP-server installs still work via an embedded Kind cluster the quickstart entrypoint provisions).
- `api-k8s` — specs that need genuine host-cluster behavior a lite container can't fake: host `kubectl` access (`image-pull-secrets`), `NetworkPolicy` enforcement (`ssrf-protection`, `jwt-propagation`), or Helm-deployed fixture servers (`oauth-self-hosted`, `mcp-enterprise-managed`) — these run against the full Kind+Helm CI environment.
- `quickstart` — a pristine, key-less first-run onboarding flow; deliberately isolated because the lite environment (used by `api`/`chromium`) pre-seeds provider keys, so it can never be in the state `@quickstart` specs need.
- `vault-k8s`, `credentials-with-vault`, `identity-providers` — dedicated projects for tests that manipulate global secrets-manager or IdP state and can't safely interleave with the shared suite.

**External-API mocking via WireMock, not in-process fakes.** Rather than stubbing LLM provider clients inside the backend process, e2e tests point the backend's real provider base URLs (`ARCHESTRA_OPENAI_BASE_URL`, `ARCHESTRA_ANTHROPIC_BASE_URL`, etc.) at a WireMock instance on port 9092, with stub mappings under provider-prefixed paths (`platform/helm/e2e-tests/mappings/`). This means the *actual* HTTP client code, retry logic, and streaming/SSE parsing run unmodified against a scripted upstream — the same principle as backend MSW boundary-mocking, but at the deployed-stack level. Locally, `tilt trigger e2e-test-dependencies` deploys the `helm/e2e-tests` chart (WireMock, Keycloak with pre-seeded test users, Vault, mock MCP servers) via `dev/Tiltfile.test`; CI uses a Kind cluster + Helm (`.github/kind.yaml`, `.github/values-ci.yaml`).

**Image reuse.** `platform/e2e-tests/playwright.config.ts` opens with a note that nothing under `e2e-tests/` is part of the Docker image being tested — CI's image-reuse cache key deliberately excludes the e2e test directory so an e2e-only change reuses a previously built platform image instead of triggering a full rebuild (`.github/workflows/platform-e2e-tests.yml`).

**Merge-queue gating, not every push.** Both the heavy backend-unit-test shards and the full e2e suite are gated to run only in the merge queue or when a PR carries an explicit label (`run-unit-tests`, `run-e2e`) — not on every ordinary PR push. `.github/workflows/on-pull-requests.yml` documents the mechanism in detail: the job's `if` condition makes it report **skipped** under its own name on an unlabeled push, and GitHub treats a skipped check as satisfying a required status check, so the branch-protection gate stays green without actually running the suite — but on `merge_group` events the guard is always true, so the queue genuinely validates before merge. The comments explicitly warn against adding same-named "placeholder" twin jobs for non-matrix checks, because a skipped placeholder would also satisfy the required check on `merge_group` even when the *real* job fails — this pattern is called out as having previously let red e2e merge past the queue.

## Rust checks

Two separate Rust surfaces get separate CI jobs: `platform-rust-checks` (the NAPI crates under `platform/archestra-rs`, `cargo check` against musl targets plus `cargo deny` for dependency policy) and `ai-labs-rust-checks` (`cargo fmt`, `cargo check`, `cargo clippy -D warnings`, `cargo test` for the standalone `ai-labs/` workspace — see [AI Labs Benchmark](./13-ai-labs-benchmark.md)). Both are merge-queue-gated the same way as the backend/e2e suites.

## `drizzle-migration-linter`: a custom rolling-deploy safety linter

`platform/drizzle-migration-linter/` (`@archestra/drizzle-migration-linter`, its own pnpm workspace package with independent tests and type-checking) lints Drizzle-generated PostgreSQL migration SQL for changes unsafe during a rolling deploy — i.e., a window where old and new application code run against the same schema simultaneously. Its README frames the goal explicitly as matching the deployment discipline of tools like [`django-migration-linter`](https://github.com/3YOURMIND/django-migration-linter).

**Error-level rules** (block CI): `DROP TABLE`, `DROP COLUMN`, table/column rename, `ALTER COLUMN ... SET NOT NULL`, `ALTER COLUMN ... TYPE`, adding a `NOT NULL` column without a `DEFAULT`, dropping constraints/indexes, adding uniqueness, adding a validating constraint without `NOT VALID`, dropping/renaming types.

**Warning-level rules** (surfaced but non-blocking): `CASCADE`, `CREATE INDEX` without `CONCURRENTLY` (locks writes on large tables), unbounded `UPDATE`/`DELETE`.

An explicit override comment (`-- drizzle-migration-linter: allow-breaking` plus a required `reason=`) suppresses error-level rules for reviewed contract migrations — typically the final step of an *expand/contract* pattern: add a nullable column, ship code that writes both and reads new-with-fallback, backfill, ship code that reads only the new column, then drop the old column with an explicit override. The README explains why this is a standalone CLI rather than a `drizzle-kit` plugin: Drizzle Kit doesn't expose a stable migration-lint hook, so a portable standalone CLI run in CI was the simpler integration surface. It runs via `drizzle-kit check` in the `platform-lint-and-unit-tests` job, in parallel (backgrounded) with codegen so it doesn't serialize the critical path.

## Performance benchmarking: `platform/benchmarks/`

Distinct from `ai-labs/archestra-bench` (an *agentic* eval — see [AI Labs Benchmark](./13-ai-labs-benchmark.md)), `platform/benchmarks/` is a plain HTTP throughput/latency benchmark using Apache Bench against the deployed platform, driven by GCP VMs (`setup-gcp-benchmark.sh` provisions an `archestra-platform-vm` and a `loadtest-vm`; `run-benchmark.sh` drives the load). Provider traffic is satisfied by the same WireMock mapping style e2e tests use (`helm/e2e-tests/mappings/openai-benchmark-chat-with-tools.json`) so the benchmark measures Archestra's own proxy/gateway overhead, not third-party API latency — "no real provider traffic is involved," per its README. It measures throughput (req/s), mean latency, and P50/P95/P99 latency across two scenarios (`simple_chat`, `chat_with_tools`) and can be run locally against a dev Tilt stack for quick iteration, or against GCP VMs for a controlled measurement.

## Orchestration: Turborepo task graph and caching

`platform/turbo.json` defines the monorepo task graph consumed by every `pnpm <script>` at the workspace root (`pnpm lint` → `turbo lint`, `pnpm test` → `turbo test`, etc., per `platform/package.json`). Key task-shaping decisions:

- **`test` and `test:e2e` are `cache: false`** — test outputs are not meaningfully cacheable in the way a build artifact is (a green run today says nothing about a rerun with a mutated database or live external state), so Turbo always executes them rather than serving a stale cache hit.
- **`lint`, `type-check`, `check:ci`, `knip`** declare explicit `inputs` (source globs plus config files like `knip.config.ts`, `package.json`, and `src/database/migrations/**`) so Turbo's remote cache can skip re-running these when the relevant files haven't changed — this is where CI gets its speed for repeated pushes to the same PR.
- **`@backend#check:ci` depends on the Rust NAPI crate builds** (`@archestra/app-runtime-rs#build`, `@archestra/sandbox-rs#build`), which are `cache: false` themselves (native builds aren't portably cacheable across the matrix of target platforms) — so a backend check always rebuilds its native dependencies fresh, but the backend's own TS/lint/type-check work is still cache-eligible.
- **`db:migrate`** scopes its `inputs` to `backend/src/database/**/*.ts` specifically, so a change anywhere else in the backend doesn't invalidate a migration-application cache entry.

CI wires Turbo's remote cache via `TURBO_TOKEN`/`TURBO_TEAM` secrets in `.github/workflows/on-pull-requests.yml`, but **fork PRs run without those secrets** (GitHub withholds secrets from fork-originated workflow runs) — the workflow's Rust setup comments note this explicitly, since it means fork PRs actually invoke `cargo build` instead of hitting a cache, which is why the Rust toolchain sync step exists as a serialized-then-retried fallback (parallel `cargo` builds triggered by Turbo's task graph would otherwise race a concurrent `rustup` download of the same toolchain and fail).

## The PR pipeline, end to end

`.github/workflows/on-pull-requests.yml` is the primary gate. Every PR push (unconditionally) runs: release-freeze check, license compliance, supply-chain policy, docs-image/docs-link checks, `migration-kit-checks` (see [Migration Kit](./14-migration-kit.md)), dependency review, and **`platform-lint-and-unit-tests`** — which runs `turbo check:ci --filter=!@backend` plus `turbo check:commit --filter=@backend` (the backend's checks minus its Vitest suite, which is split out into its own sharded job so it doesn't serialize behind the largest suite), a full production build (`pnpm build` — validates the Next.js build, backend build, and Rust NAPI compile together), and a migration-validation script that runs `drizzle-kit check` in the background while `pnpm codegen && pnpm lint:fix` runs in the foreground, then fails the build if either codegen or `pnpm db:generate` would produce an uncommitted diff (i.e., a schema change without its matching migration file, or stale generated API-client code).

Heavier suites — `platform-rust-checks`, `ai-labs-rust-checks`, the 4-way sharded `backend-unit-tests`, and `frontend-integration-tests` — are merge-queue-only (or `run-unit-tests`-labeled), per the skip-as-pass mechanism described above. `helm-chart-linting-and-tests` (Helm lint + `helm unittest`) runs on every push, since it's cheap and independent of the pnpm/cargo toolchains. `.github/workflows/platform-e2e-tests.yml` runs the full e2e matrix similarly gated to merge-queue/`run-e2e`-label, with a nightly (`schedule: cron "0 3 * * *"`) full cross-browser run that additionally exercises the firefox/webkit projects the merge-queue path skips.

## Design Decisions & Tradeoffs

- **PGlite over mocking the database.** *Rationale:* real Postgres semantics (constraints, cascades, JSON column behavior, actual Drizzle-generated SQL) catch a class of bugs a mocked ORM interface structurally cannot; `platform/CLAUDE.md` states this as a hard rule ("never mock database interfaces in backend tests"). *Cost:* every test file pays a WASM-Postgres startup cost and the suite needs the two-stage snapshot/truncate machinery (`global-setup.ts` + `setup.ts`) purely to keep that cost tractable at 400+ files — a mocked DB would have been instant everywhere, at the price of testing a fiction.

- **Shared-worker `clean` project vs. fully isolated `mocked` project.** *Rationale:* module-graph import cost, not per-test logic, dominates the suite's wall-clock time, and `vi.mock`'s process-wide registry can't safely reset between files sharing a worker — so the split lets mock-free files (the majority) skip re-importing the whole backend per file. *Cost:* the split is a real behavioral fork, not just a speed knob — the `clean` project needs the config-restore machinery in `setup.ts` to prevent cross-test/cross-file state leakage that isolated tests get for free, and a contributor must understand *why* adding a `vi.mock` silently changes which project a file lands in.

- **WireMock (not in-process fakes) for e2e external-API mocking.** *Rationale:* faking at the HTTP boundary — same principle as backend MSW usage — means the actual provider-client code (streaming parsers, retry/backoff, auth headers) runs unmodified in the system under test; an in-process fake would only ever exercise the code path the fake author remembered to stub. *Cost:* e2e runs now depend on a full sidecar service (WireMock) and its mapping files (`helm/e2e-tests/mappings/`) as a maintained artifact, and a stub mismatch (wrong path prefix, wrong response shape) fails loudly but adds a layer contributors must learn.

- **Turbo caching disabled for `test`/`test:e2e` but enabled for `lint`/`type-check`/`check:ci`.** *Rationale:* static analysis is a pure function of source content, so cache hits are trustworthy; test execution against live/mutable state (a database, a deployed cluster) is not something Turbo can safely represent as cacheable without risking false-green results. *Cost:* the full test suites always pay their full wall-clock cost on every run that needs them — which is part of why they're additionally gated to merge-queue/label rather than every push, stacking a scheduling optimization on top of the caching one.

- **Skip-as-pass gating for heavy suites, guarded against placeholder-twin jobs.** *Rationale:* running the full backend shard matrix, Rust checks, and e2e suite on every keystroke-triggered PR push would make CI prohibitively slow for a large monorepo; GitHub's "a skipped required check passes" behavior lets a job report success-by-absence on ordinary pushes while still running for real in the merge queue. *Cost:* this is a sharp-edged mechanism — the workflow comments record a specific past incident where a same-named placeholder job masked a real failing job's `merge_group` result, so the pattern requires ongoing vigilance from anyone adding a new gated job, not just a one-time setup.
