# AI Labs: The `archestra-bench` Agentic Benchmark

`ai-labs/` is a standalone Rust workspace, separate from the `platform/` pnpm monorepo, reserved for AI-feature prototyping at Archestra. Today its sole resident is **archestra-bench**: an agentic benchmark and trajectory generator that measures whether Archestra itself — the product, not a raw model — correctly assembles a skill + MCP + agent surface and drives an agent through realistic, multi-stage sessions (`ai-labs/README.md`). This is a different kind of "benchmark" than `platform/benchmarks/`, which is a plain HTTP-throughput load test; see [Testing Strategy](./12-testing-strategy.md) for that one. For the sandbox/skills machinery archestra-bench is exercising, see [Agents, Skills & Sandbox](./07-agents-skills-sandbox.md).

## Scope: an internal product eval, not a leaderboard

The README states this explicitly as a non-goal: "chasing a public leaderboard is an explicit non-goal." The asset the team invests in is native tasks derived from real Archestra workflows — each one doubling as permanent regression protection for a specific product capability (skill loading, MCP tool discovery, cross-conversation file persistence, sandbox code execution) rather than a generic reasoning benchmark that happens to run through Archestra's chat API. This framing shapes almost every other design choice below.

## Protocol: environments, tasks, and out-of-band grading

Tasks are grouped into **environments** — `envs/<id>.toml` files that each declare a bundle of web-pinned skills, remote MCP servers, and a single agent, plus a list of task ids. For each environment the harness:

1. Boots a **fresh, isolated Archestra backend** on a new port, over a fresh, freshly-migrated database on a dedicated bench Postgres instance the runner provisions itself.
2. Seeds that backend's surface: a provider key + models, the environment's pinned skills, its remote MCPs, the harness-owned benchmark MCP, and creates the environment's agent with its tool surface locked.
3. For each `task x model` pair, drives the task's ordered conversation stages (e.g. "user asks X → then corrects to Y") through real agentic chat sessions, saving the full trajectory as coalesced message-level events.
4. Reads the agent's submission (downloading a produced file artifact too, for file-output tasks) and grades it **out of band**.
5. Drops the database and kills the backend process.

Results aggregate by environment and by task.

**The submission tool is a format gate, not a grader.** The agent turns in its answer by calling the benchmark MCP's `submit_result` tool, which checks only that the payload matches the task's JSON schema — a malformed submission gets a structured error back so the model can self-correct within its own tool loop, bounded by a small attempt budget. Real correctness is checked separately, by a `pytest` verifier that **never enters the sandbox or the MCP surface the agent operates in** — so the agent has no path to read its own grading logic or otherwise game it. The verifier reads fixed environment variables the harness sets: `BENCH_RESULT` (the submitted JSON, always set), `BENCH_FIXTURES` (a directory of task `inputs/`/`expected/`, when either exists), `BENCH_OUTPUT` (a file the agent exported via `download_file`, for artifact-producing tasks), and `BENCH_STATE` (a JSON snapshot of backend REST state plus the run's ordered tool calls, for tasks whose effect is *backend state* rather than a returned value — e.g. "did the agent create a skill," "how many tools/skills have a name matching X").

A task directory (`tasks/<id>/`) separates `inputs/` (staged into the agent's sandbox and readable by the verifier) from `expected/` (verifier-only ground truth that is never staged to the agent — a file's `src` is confined to `inputs/` at load time specifically so a precomputed answer can't leak in). Verifiers run in their own ephemeral `uv` environment per task, with a shared stdlib helper (`bench_verifier.py`) exposing `result()`, `state()`, `output()`, `fixtures(*rel)`, and `read_fixture_json(*rel)` so individual verifiers read the contract through a stable API instead of re-deriving the env-var plumbing themselves.

## Reproducibility: two variance-reduction knobs, not bitwise determinism

- **Pinned sampling temperature (`0.0`)** on every chat request the harness sends. The README is explicit that this is variance *reduction*, not determinism — MoE routing and parallel tool-call ordering keep agent runs non-bitwise-stable even at temperature 0. A provider that can't honor the parameter (e.g. certain reasoning models) drops it with a warning rather than erroring.
- **Optional remote-MCP tool-surface pinning** via a committed `envs/<id>.mcp.lock` file (MCP name → sorted tool short-names). Remote MCP servers can silently add, rename, or remove tools over time, which changes the agent's action space without anyone editing the benchmark — a drift from the lock aborts that environment's setup with a per-MCP diff, rather than silently grading against a shifted surface. Pinning is opt-in (an environment without a lock file runs unchanged), and it pins the tool *surface* only — response bodies stay live by design, since several tasks (e.g. `crypto-price`, `github-stars`) deliberately require fetching genuinely live data.

## Outcomes

Each `(environment, task, provider, model)` cell resolves to exactly one of: `passed`/`failed` (a well-formed result was submitted and the verifier accepted/rejected it), `format_failed` (the agent never matched the schema within its attempt budget), `no_submission` (the run finished without calling `submit_result` at all), or `agent_error` (the chat run itself errored before grading — an `infra:`-prefixed variant marks a backend/boot failure for that lane specifically, so sibling lanes aren't treated as failed by association).

## The harness: a Rust binary with five subcommands

`archestra-bench` (built via `cargo build --release`) exposes `benchmark` (run the sweep), `analyze` (turn a finished run into a Tier-1/Tier-2 recommendations report — see the `archestra-dev-bench-analysis` project skill for a Claude-subagent-driven alternative that needs no API key), `full` (both, back to back), `prepare` (render a run manifest for external analysis without any LLM calls), and `dashboard` (serve a local read-only dashboard over past runs).

**Lanes** (`lanes.toml`) are named `(provider, model, base_url, api_key_env)` endpoints — the actual sweep is `environment x lane`, and a lane's optional `base_url`/`api_key_env` let two lanes share a provider through different gateways or keys (e.g. an Anthropic-compatible third-party gateway). `--lanes` selects a subset by name; `--max-workers` bounds concurrent lanes (default one worker per selected lane, capped at 4), with tasks inside a lane running serially.

**A/B testing via `--branch`.** Passing `--branch <ref>` (or `ARCHESTRA_BENCH_BACKEND_BRANCH`) fetches `origin/<ref>`, checks it out into a throwaway git worktree, runs a full `pnpm install --frozen-lockfile && pnpm build` there, and spawns every environment's backend from that build instead of the working tree — one build shared across all environments in the run. This lets a contributor benchmark a branch against `main` (or against the dev-tree working state) without a second Tilt stack or manual environment surgery; the backend simply reads `process.env` for its DB URL, ports, and Dagger host, so per-environment overrides need no `.env` edits.

**Dagger host resolution ladder.** Before booting a backend the runner needs a Dagger code-runtime engine (the same sandbox execution backend used by [Agents, Skills & Sandbox](./07-agents-skills-sandbox.md)), and resolves one via a strict fallback: (1) `ARCHESTRA_CODE_RUNTIME_DAGGER_RUNNER_HOST` if set, used verbatim with no further searching — this is how the prod-image CI path supplies a `kube-pod://` host; (2) otherwise, if Docker is running and the engine image is already pulled, bring up a runner-managed engine via `dev/docker-compose.bench-dagger.yml`; (3) otherwise, fall back to the dev stack's own port-forwarded engine at `tcp://127.0.0.1:1234`; (4) otherwise **abort immediately**, naming every tier it tried and the remedy, rather than hanging or silently degrading. The managed engine (tier 2) is deliberately left running between runs so its buildkit cache stays warm.

## Task-authoring discipline (`ai-labs/CLAUDE.md`)

A separate document, `ai-labs/CLAUDE.md`, governs how new tasks get written — describing itself as "the discipline, not the plumbing." Three rules stand out as anti-Goodhart measures:

- **The prompt must read like a real user's ask.** No mention of the sandbox, `run_command`, `search_tools`, `/home/sandbox` paths, or "the verifier." The prompt names only the delivery-protocol tools the harness actually grades through (`submit_result` always; `download_file` for file-output tasks) — never a task-*solving* tool like `create_skill` or a specific skill name, because finding the right tool is itself a capability under test. Most pointedly: **the agent must never learn it is inside a benchmark at all** — no "benchmark," "eval," "test," "graded," or "fixture" language anywhere the agent can see, including the skills and files a task loads. A real user with a corrupted blob wants it decoded; they don't say "the benchmark blobs."
- **No trap warnings, no telegraphing emphasis.** Instructions like "be careful to…" or bolding the exact quantity being checked hand the model the answer shape for free — CLAUDE.md forbids both.
- **The verifier is a strict, non-coercing oracle.** It extracts the submitted value exactly and never salvages a malformed or stringified answer — a wrong format is treated as a genuine capability signal, not noise to smooth over. It checks the real mechanism (actual GIF frame count, not a π value a model could recite from memory), and `expected/` ground truth is computed from fixtures rather than hardcoded wherever possible. There's also an explicit **difficulty floor**: if a weak model scores 100%, the task is leaking information or trivial, and should be de-clued or strengthened rather than left as-is.

## Prod-image CI mode

The daily scheduled benchmark run (`.github/bench/`) runs this same harness against the *deployed* platform Docker image rather than the dev repo, via three env-var-driven differences documented in `ai-labs/CLAUDE.md`: `--platform-dir`/`ARCHESTRA_BENCH_PLATFORM_DIR` points at `/app` (the prod image's layout) instead of `<repo>/platform`, conflicting with `--branch`/`ARCHESTRA_BENCH_BACKEND_BRANCH` since the two describe mutually exclusive "where does the backend come from" answers; `ARCHESTRA_BENCH_MIGRATE_CMD` runs `drizzle-kit migrate` directly since the prod image has no `pnpm`; and the Dagger runner host/CLI-bin pair arrive strictly via process environment (force-overwritten by `build_backend_env`) rather than `/app/.env`, so container-level feature-flag env vars still flow through but the sandbox wiring can't be silently overridden by a stale `.env`.

## Design Decisions & Tradeoffs

- **Internal product eval, explicitly not a public leaderboard.** *Rationale:* the value proposition is regression protection for Archestra's own skill/MCP/agent assembly, not comparative model rankings that a generic benchmark already covers better. *Cost:* the task set is small and Archestra-specific by design, so it can't be used to make general claims about model capability, and every new task requires bespoke authoring discipline rather than importing an existing public dataset.

- **Out-of-band verification the agent can never see or game.** *Rationale:* a grader reachable from inside the agent's own tool loop is a grader the agent (or a prompt-injected payload) could eventually read, predict, or manipulate; keeping the pytest verifier entirely outside the sandbox/MCP surface makes that structurally impossible, not just policy-discouraged. *Cost:* this adds real plumbing — fixed env-var contracts (`BENCH_RESULT`/`BENCH_FIXTURES`/`BENCH_OUTPUT`/`BENCH_STATE`), a shared `bench_verifier.py` helper, and per-task `uv` environments — that a simpler "grade inside the same process" design wouldn't need.

- **Fresh, isolated backend per environment (new port, new migrated DB, teardown after).** *Rationale:* cross-task or cross-environment state leakage would silently invalidate results — a task that seems to pass because a *previous* task happened to create the resource it's checking for is a false positive that erodes trust in the whole suite. *Cost:* this is expensive: a dedicated bench Postgres, a full migration replay, and a second backend process per environment (mitigated somewhat by `share_backend = true` for environments whose tasks are proven not to mutate shared state, and by reusing an already-built `dist/server.mjs` rather than starting a competing dev-mode build).

- **Prompt-realism discipline as an explicit anti-Goodhart measure.** *Rationale:* an agent that can detect it's being evaluated (via benchmark-flavored language, named solution tools, or trap-warning emphasis) will behave differently than it would for a real user — optimizing for the test rather than demonstrating the underlying capability the test is a proxy for. *Cost:* this makes tasks harder to write and review — a task author must resist the natural instinct to spell out exactly what's being checked, and reviewers must actively hunt for accidental tells rather than just checking the verifier logic is correct.

- **Temperature pinning as variance reduction, not a determinism guarantee.** *Rationale:* cutting variance at the source (a fixed sampling parameter) is cheaper than averaging it out with more rollouts per cell, and the README is careful not to oversell what pinning buys — MoE routing and parallel tool-call ordering mean two runs of the same config can still diverge. *Cost:* results still require some tolerance for run-to-run noise; a single `passed`/`failed` outcome on a borderline task is not a fully deterministic signal, and the team accepted that rather than paying for expensive multi-rollout averaging.
